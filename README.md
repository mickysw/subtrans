# subtrans

영어 영상에 한국어 자막을 달아 **화면에 구워** 내보내는 도구.
유튜브 링크 하나를 넣으면 자막이 박힌 mp4가 나온다.

```
python run.py "https://www.youtube.com/watch?v=..."      # 받기 → 받아쓰기 → 번역 → 검수화면
python run.py "https://www.youtube.com/watch?v=..." --burn   # 검수 후 굽기
```

> ⚠️ **본인이 권리를 가졌거나 사용 허락을 받은 영상에만 사용하세요.**
> 타인의 영상을 무단으로 재배포하는 것은 저작권 침해가 될 수 있습니다.

---

## 무엇이 어려운 문제인가

자막 자동 생성은 두 가지를 동시에 만족해야 한다.

1. **말하는 시점과 자막이 정확히 맞을 것**
2. **사람이 실제로 말한 깨진 문장을, 의도를 살려 번역할 것**

이 둘은 서로 다른 기술로 풀어야 하고, **섞으면 둘 다 망가진다.**

LLM에 영상을 통째로 주고 자막 파일을 만들게 하면 편하지만, 긴 오디오에서
타임스탬프가 뒤로 밀린다([보고된 사례](https://github.com/jianchang512/pyvideotrans/issues/624)).
그래서 이 도구는 **시간은 받아쓰기 엔진이 재고, LLM은 번역만** 한다.

---

## 핵심 설계 3가지

### 1. 자막의 시각은 계산하지 않고 관측한다

받아쓰기 엔진(`faster-whisper`, `word_timestamps=True`)이 **단어 하나하나의 시작·끝 시각**을 준다.
자막 한 장의 시각을 이렇게 못 박는다.

```
시작 = 그 장 첫 단어의 시작 시각
끝   = 그 장 마지막 단어의 끝 시각
```

추정이 개입하지 않으므로 싱크가 어긋날 여지 자체가 없다.

### 2. 자막을 끊는 자리는 규칙으로 정한다

문장부호 > 긴 무음 > 접속사 앞 > 길이 강제 순으로 점수를 매겨 가장 좋은 자리에서 끊는다.
**문장이 끝난 자리는 절대 넘지 않는다** — 화자가 바뀌는 자리이기도 해서,
넘으면 서로 다른 사람의 대사가 한 자막에 들어간다.

### 3. 액자를 두를 때 영상을 축소하지 않는다

원본을 액자 안에 넣으려면 보통 축소한다. 그러면 1080p 영상이 실질 918p가 된다.
대신 **캔버스를 키운다.**

```
캔버스  2560 x 1440
영상    2176 x 1224   ← 원본 1920x1080을 확대해서 배치 (폭의 85%)
```

덤이 있다. 유튜브는 1440p 이상 업로드에 더 좋은 코덱과 높은 비트레이트를 배정하므로,
**1080p로 보는 시청자에게도 더 선명해진다.** 액자가 화질을 깎는 게 아니라 올려준다.

## 엔지니어링 기록

### 측정으로 찾아낸 결함

눈으로 보면 다 멀쩡해 보였다. 수치로 재고 나서야 드러난 것들.

| 결함 | 전 | 후 |
|---|---|---|
| 서로 다른 화자의 대사가 한 자막에 붙음 | 19장 | **0장** |
| 최소 길이 보장 로직이 다음 자막을 침범 | 겹침 2건 | **0건** |
| 줄바꿈 누락으로 한 줄이 화면을 넘김 | 21줄 | **0줄** |
| 의존명사 앞에서 끊김 (`처음 시작할 / 때`) | 다수 | **1장** |
| 화질 측정 소요 시간 (20분 영상 기준) | 1시간+ | **약 5분** |

### 화질 측정이 틀렸다는 걸 밝혀낸 과정

가장 시간을 많이 쓴 문제이고, 결론이 뒤집힌 문제다.

**1. 증상** — 결과물의 VMAF가 92점. 목표 95에 미달. 특히 한 구간이 85점.

**2. 첫 시도** — 압축을 강화했다(CRF 17 → 14).
결과: **0.38점** 상승, 파일 크기 46% 증가(236MB → 345MB). 지렛대가 듣지 않는다.

**3. 원인 분리** — 지렛대가 안 들으면 원인을 잘못 짚은 것이다. 하나씩 갈랐다.

| 무엇을 쟀나 | VMAF | 판정 |
|---|---|---|
| 확대→축소 왕복만 (압축 없음) | 98.4 | 리샘플링 아님 |
| 확대 없이 액자만 | 98.7 | 확대 손실은 0.3점뿐 |
| 자막 영역을 제외하고 비교 | 85.4 | 자막도 아님 |

세 가설이 모두 기각됐다. 손실은 압축 쪽인데 압축을 줄여도 안 오른다 — 모순이다.

**4. 남은 가설** — 문제가 결과물이 아니라 **측정 방법**에 있다면?

측정할 때 `-ss`로 두 파일의 같은 시각을 찾아간다. 두 파일은 키프레임 위치가 달라
**1프레임씩 어긋날 수 있고**, VMAF는 그 어긋남을 큰 손상으로 센다.
그렇다면 움직임이 많은 장면에서만 점수가 무너지는 것도 설명된다.

**5. 검증** — 탐색을 쓰지 않고 처음부터 디코딩해 같은 구간을 비교했다.

```
-ss 로 탐색:        85.1
처음부터 디코딩:    97.4    ← 같은 구간, 같은 파일
```

측정이 틀렸던 것이다. `select` 필터로 구간을 고르는 방식으로 교체하고
CRF는 17로 되돌렸다. **당시 실측 97.12점** (이 값은 뒤에서 뒤집힌다).

> 얻은 교훈: 지렛대를 당겼는데 반응이 없으면, 지렛대가 약한 게 아니라
> **자를 의심해야 한다.** 그러지 않았으면 파일만 46% 키운 채 "화질 미달"로 결론지었을 것이다.

### 그리고 그 기준선마저 틀렸다 (2라운드)

97.12점은 5분 테스트 클립에서 나온 값이었다. 26분 전체를 돌리자 **81.5점**이 나왔다.
같은 설정, 같은 영상인데.

차이는 원본이었다. 클립은 다운로드 방식 때문에 h264(저화질 계열)를 받았고,
전체 다운로드는 VP9를 받았다. **원본이 좋아지면 재현 난이도가 올라간다.**

이번에도 하나씩 갈랐다.

| 무엇을 쟀나 | VMAF |
|---|---|
| CRF 17 → 14 → 11 | 85.9 / 86.1 / 86.3 (비트레이트 3배인데 +0.37) |
| 확대→축소 왕복만 (압축 없음) | 98.1 |
| 압축 손실만 격리 (무손실 액자 기준) | 88.7 (5.5Mbps) / 88.9 (8.6Mbps) |

8.6Mbps를 써도 89점에서 멈춘다. 숫자로는 설명이 안 됐다.

**그래서 눈으로 봤다.** 원본과 결과물에서 같은 시각의 화면을 1:1 픽셀로 잘라 비교했다.
옷의 글자, 마이크 라벨, 케이블 디테일까지 **구분되지 않았다.**

원인은 2차 인코딩의 성질이었다. 이미 압축된 영상을 다시 인코딩하면 인코더가 원본의
압축 잡음을 매끄럽게 다듬는데, **사람 눈에는 개선이거나 무의미하지만 VMAF는 손상으로 센다.**
VMAF 95는 원본 소스를 처음 인코딩할 때의 기준이지, 재인코딩에 쓸 기준이 아니었다.

그래서 게이트의 성격을 바꿨다. **"화질이 좋다"의 기준이 아니라 "설정이 망가졌다"의 기준**으로.
임계값 80, 그리고 낮을 때 CRF를 낮추라고 하던 안내를 지웠다 — 효과 없음이 두 번 측정됐으므로
그건 틀린 조언이었다. 대신 해상도가 줄지 않았는지, 프레임레이트가 같은지를 확인하라고 바꿨다.

> 얻은 교훈 2: 자를 고쳤다고 끝이 아니다. **그 자가 무엇을 재도록 만들어졌는지**도 맞아야 한다.
> 그리고 숫자가 설명을 멈추면, 그때는 직접 눈으로 봐야 한다.

### 번역 비용을 18배 줄인 방법

처음엔 Claude Code를 헤드리스(`claude -p`)로 호출해 번역했다. 재보니:

```
실제 번역 프롬프트      약  2,000 토큰
호출 1번당 실제 입력    약 44,000 토큰   ← 22배
```

차이는 Claude Code가 매번 시스템 프롬프트·MCP 도구 목록·스킬 목록을 통째로 싣는 몫이었다.
`--strict-mcp-config`로 덜어봤지만 2,300 토큰만 줄었다.

두 가지로 해결했다.

1. **API를 직접 호출** — 고정비가 통째로 사라진다 (44,000 → **2,389 토큰**)
2. **묶음 크기 30 → 60** — 고정비를 나눠 쓰는 구조라, 묶음을 두 배로 해도 입력은 2,000 토큰만 는다

| | Claude Code 경유 | Gemini 직접 호출 |
|---|---|---|
| 입력 토큰 (5분 분량) | 약 220,000 | **약 7,000** |
| 소요 시간 | 90초 | **79초** |
| 자막 검사 경고 | 18건 | **4건** |
| 비용 | 구독 사용량 소모 | **무료 등급** |

품질도 떨어지지 않았다. 오히려 줄바꿈 규칙을 더 잘 지켰다.

### 한국어 자막 조판

한국어 자막에는 영어에 없는 제약이 있다.

- 한 줄 16자, 최대 2줄 (넘으면 화면을 벗어나거나 못 읽는다)
- 자막이 화면에 머무는 시간에 맞춰 글자 수 상한을 계산해 **프롬프트에 함께 넣는다**
  (`2.4초짜리 자막 → 최대 12자`). 번역기에게 지면의 크기를 알려주는 셈이다
- 줄을 나눌 땐 **의존명사를 앞말에서 떼지 않는다** — `처음 시작할 / 때` 는 읽기 어렵다

## 파이프라인

각 단계 결과가 `work/<영상id>/` 에 남아 끊긴 지점부터 다시 돌아간다.

| | 단계 | 도구 | 결과물 |
|---|---|---|---|
| ① | 받기 | yt-dlp | `video.mkv`, `audio.wav` |
| ② | 받아쓰기 | faster-whisper | `words.json` |
| ③ | 조각내기 | 규칙 기반 | `en.srt`, `cues.json` |
| ④ | 번역 | Gemini (또는 Claude) | `ko.srt` |
| ⑤ | 검사 | 자체 게이트 | 통과 / 반려 목록 |
| ⑥ | 검수 | 브라우저 화면 | `review.html` |
| ⑦ | 액자 + 굽기 | ffmpeg | `out.mp4` |

**⑤ 검사 게이트** — 사람이 보기 전에 기계가 먼저 거른다.
번역 결과의 장수가 원본과 다른지(LLM이 줄을 먹거나 합침), 읽기 속도가 너무 빠른지,
자막끼리 시간이 겹치는지, 번역 안 된 영어가 남았는지.

**⑥ 검수 화면** — 서버 없이 여는 HTML 한 장. 자막 줄의 시각을 누르면 영상이 그 시점으로
점프하므로 싱크와 오역을 한 자리에서 본다. 글자만 고치고, 타임코드는 건드리지 않는다.

## 성능 (실측, i5-12400 6코어 / GPU 없음)

| 단계 | 5분 클립 | 20분 영상 환산 |
|---|---|---|
| 받아쓰기 | 2.8분 (실시간의 0.57배) | 약 11분 |
| 번역 | 79초 | 약 5분 |
| 굽기 (1440p) | 2.7분 | 약 11분 |
| 화질 측정 | 2분 | 약 5분 |

GPU 없이 CPU만으로 동작한다. 첫 실행 때 받아쓰기 모델 약 1.5GB를 내려받는다.

## 설치

```bash
uv venv --python 3.12 .venv
uv pip install --python .venv faster-whisper yt-dlp
cp .env.example .env        # 그리고 Gemini 키를 넣는다
```

ffmpeg가 PATH에 있어야 한다. Gemini 키는 [Google AI Studio](https://aistudio.google.com/apikey)에서
무료로 발급받는다. 키가 없으면 Claude Code(설치돼 있는 경우)로 자동 전환된다.

## 설정

| 무엇을 | 어디를 |
|---|---|
| 자막 크기·위치·색, 액자 여백·배경 | `style.json` |
| 사람 이름·팀명 번역 고정 | `glossary.json` |
| 번역 말투·규칙 | `prompts/translate.md` |
| 자막 길이, 줄당 글자수, 번역 엔진 | `config.json` |

오역이 나면 `glossary.json`에 추가하고 번역만 다시 돌린다. 받아쓰기 결과는 재사용된다.

```bash
python run.py "주소" --redo translate
```
